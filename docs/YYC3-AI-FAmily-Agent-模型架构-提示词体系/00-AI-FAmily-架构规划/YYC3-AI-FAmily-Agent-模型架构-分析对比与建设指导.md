## 摘要

本报告以「YYC3 大模型训练架构师、Agent 研发指导兼评测师」为主责角色，对目录内两份现有文档进行审核：一份是系统级提示词《001-AI-FAmily-系统级提示词.md》，另一份是《YYC3-AI-FAmily-Agent-模型架构-教科书级提示词大纲.md》。审核同时对照 2026 年提示词工程、Agent 技能、工具协议、评测基准、训练对齐与安全治理的公开标准及社区实践。

核心结论如下：

1. **方向正确，结构已具雏形。** 现有体系覆盖角色契约、能力矩阵、评测口径、回退协议、输出规范，并已提出契约、持久化、认知、技能、审计、迭代、沟通与治理八个文件域。
2. **工程化不足是主要短板。** 现有文档更接近「体系设计说明」，尚未形成可执行的 manifest、文件级契约、评测数据集、运行接口、日志台账与发布门禁。
3. **评测闭环需要从「基准列举」升级为「分层评测 + 内部黄金集 + 回归门禁」。** 公开基准适合能力体检，不能替代业务场景验收。
4. **安全治理需要从「原则声明」落到「威胁模型 + 日志字段 + 权限边界 + 合规映射」。** 尤其是系统提示词泄露、间接提示注入、工具越权与记忆污染。
5. **建议采用「1 + 8 + 3」目标架构。** 即 1 个总控清单、8 个文件域，以及评测、运行时、资产 3 个横切目录；以 manifest 作为唯一入口，以评测与台账作为闭环证据。

本报告同时复核了 DeepSeek-V4.1-Flash 对系统提示词的反馈，并将可执行建议落入系统提示词、1+8+3 大纲与行业资料索引。

本次同时完成了大纲文档的排版与更名，并修正了原文中「六个文件域」与文件树实际八个域不一致的问题。综合成熟度评估为 **3.0 / 5**（本报告判断）：体系认知合格，工程落地仍需补齐。

## 二、现状审核

### 2.1 系统级提示词：角色与评测指导

**优势：**

- 角色定义完整，明确「训练架构师 / Agent 研发指导 / 评测师」三重身份与权责边界。
- 评测维度覆盖通用语言、领域专业、推理决策、安全合规、性能效率、Agent 适配六类，并提示基准饱和与污染风险。
- 微调选型已按数据条件区分 SFT、DPO、ORPO、KTO、SimPO、RLHF/PPO，并强调对齐税检查。
- 退化排查提出 checkpoint 级三线评估：当前任务、既往任务保持度、固定参考集。
- Agent 评审覆盖基础层、能力层、决策层、编排层，并区分「模型能力问题」与「系统架构问题」。
- 输出规范要求核心结论前置、数据指标、根因分析、优化建议与风险提示，具备报告化意识。

**不足：**

- 缺少可执行的 **file-level manifest**：没有唯一入口说明各文件职责、依赖、补全顺序与验收标准。
- 缺少 **运行时状态机**：会话如何开启、续接、挂起、关闭，状态如何落盘，尚未形成可执行协议。
- 缺少 **工具权限模型**：工具最小权限、写操作人工确认、递归深度上限、工具调用失败处理尚未落地。
- 缺少 **日志与台账 schema**：评审结论、训练落档、评测运行记录没有统一字段与保留策略。
- 缺少 **评测数据集设计**：没有内部黄金集、用例矩阵、回归集与发布门禁。
- 缺少 **安全威胁模型**：对系统提示词泄露、间接注入、记忆污染、工具投毒缺少结构化防御。
- 部分概念仍偏抽象，例如「证据充分性」「业务落地」缺少可判定的评分锚点。

### 2.2 教科书级提示词大纲

**优势：**

- 文件树清晰，按契约、持久化、认知、技能、审计、迭代、沟通、治理八个域组织，覆盖面完整。
- 每个文件给出章节要点与行业标准锚点，具备较强的可补全性。
- 已提出 L1–L3 摘要、四层记忆、上下文预算、技能渐进式披露、日志两级结构、决策台账、变更传播等关键机制。
- 明确「程序记忆不得自动写入」「摘要必须可追溯」「日志区分元数据与内容」等高价值约束。
- 补全建议强调按 manifest 顺序、逐文件校验、最终做交叉一致性检查，方法论正确。

**不足与已修正项：**

- **已修正：域数量不一致。** 原文称「六个文件域」，但文件树实际包含 `01-AI-FAmily-契约层` 至 `08-AI-FAmily-治理层` 八个域。本次已统一为「一个总控清单 + 八个文件域」。
- **manifest 缺失可执行模板。** 当前只有 YYC3-AI-FAmily-Agent-模型架构-总控清单 的章节描述，没有字段、依赖图、验收清单与版本记录格式。
- **文件级契约不足。** 各域只有章节标题，没有输入、输出、失败模式、依赖、验收标准的统一 schema。
- **评测与运行时未单列。** 评测、运行时适配、黄金集、CI 门禁被分散在多个域中，缺少独立资产与执行入口。
- **安全治理偏原则。** 对 OWASP、NIST、EU AI Act、国内规定的映射尚未形成可检查条款。
- **成本与延迟未建模。** 没有 token 预算、工具调用预算、P95 延迟、单任务成本等运行指标。
- **待验证的模型规格表述。** 大纲中关于 DeepSeek V4.1 Flash 的 1M 上下文窗口与 8B/16B 激活结构，需以官方模型卡或技术报告校准；在未确认前按「待验证」处理，不作为容量规划与成本估算的唯一依据。

## 三、行业标准与技术对比

### 3.1 提示词工程：从「写长」转向「写规格」

OpenAI 的提示词指南强调清晰指令、角色设定、分隔符、步骤化、示例与输出长度控制[cite:1]。Anthropic 进一步指出，提示词工程开始前应先定义成功标准并有可经验测试的评估方式；结构化标签、示例、思考与提示链是核心手段[cite:2]。

2026 年一个值得注意的变化是「上下文工程」而非「提示词堆叠」。Anthropic 公开说明，面向新一代模型，Claude Code 的系统提示词被削减超过 80%，在编码评测上没有可测量的损失[cite:3]。这说明：**系统提示词应承担规格、边界与判据，具体流程应下沉到技能、工具与运行时**。

Microsoft HVE Core 把提示词定义为「单会话工作流定义」，使用 YAML frontmatter 与 Markdown 正文，并通过 HVE Builder 的 create / improve / review / refactor 模式运行质量门禁[cite:4]。这与 YYC3 的「manifest + 文件域」方向一致，但 HVE 更强调**可评审、可重构、可复用**的工程流程。

**对 YYC3 的启示：**

- 系统提示词保持「角色 + 判据 + 回退 + 输出契约」，不要承载全部流程。
- 流程性内容放入技能文件，按需加载，减少上下文占用。
- 每个提示词文件应有 YAML frontmatter、适用范围、输入输出、失败模式与验收标准。

### 3.2 Agent 技能与工具协议

Anthropic 的 Agent Skills 以 `SKILL.md` 为核心，要求 YAML frontmatter 至少包含 `name` 与 `description`，并允许附带脚本、参考文件与工具；技能应聚焦一个可重复的任务[cite:5][cite:20]。这与「技能注册表 + 渐进式披露」高度一致。

工具协议方面，MCP 负责 Agent 与工具/数据源的连接，A2A 负责 Agent 与 Agent 之间的发现、委派与协作；A2A 由 Google 发起并捐赠给 Linux Foundation，MCP 与 A2A 是互补关系[cite:6][cite:7][cite:22]。

**对 YYC3 的启示：**

- 技能注册表应记录 `name`、`description`、输入/输出 schema、版本、依赖、失败模式。
- 工具调用必须有最小权限、参数校验、无关性检测、失败分类与人工确认闸门。
- 多 Agent 协作应明确「委派方对最终证据等级负责」，不得把子 Agent 输出直接提升为「已验证」。

### 3.3 评测体系：公开基准 + 内部黄金集

公开基准适合做能力体检，但不能替代业务验收。2026 年可用的代表性基准包括：

| 基准 | 侧重点 | 对 YYC3 的用途 | 注意事项 |
| ---- | ---- | ---- | ---- |
| HELM Capabilities / MMLU-Pro | 通用知识与多学科能力 | 基座模型能力基线 | 静态基准存在饱和与污染风险[cite:9] |
| LiveBench | 抗污染、客观评分、定期刷新 | 模型能力趋势监测 | 23 个任务、7 类能力，约每六个月刷新[cite:10][cite:24] |
| BFCL V4 | 函数调用与 Agent 工具使用 | 工具调用准确性、无关性检测、多轮与记忆 | 覆盖 web search、memory、multi-turn、irrelevance[cite:8][cite:23] |
| τ-bench | 工具- Agent -用户交互 | 真实业务任务的可靠性与一致性 | 强调 pass^k 多轮可靠性，而非单次 pass@1[cite:11] |
| SWE-bench Verified / Pro | 真实代码修复 | 代码 Agent 能力评估 | 需关注任务污染与评分协议[cite:12] |

社区评测实践强调：先用真实 trace 构建小数据集，离线评测通过后再上线；能用代码评估器就不用 LLM judge，LLM judge 需要人工复核；对多步 Agent 要评估完整线程、轨迹与最终状态[cite:17]。LangSmith 的实践可作为 YYC3 评测流水线的参考。

**对 YYC3 的启示：**

- 建立「公开基准 + 内部黄金集 + 线上抽样」三层评测。
- 内部黄金集按业务场景组织，覆盖正常、边界、对抗、不可达目标四类用例。
- 除准确率外，必须记录 pass^k、工具调用正确率、无关调用率、P95 延迟、单任务成本与安全违规数。

### 3.4 训练与对齐：按数据条件选方法

现有文档已列出 SFT、DPO、ORPO、KTO、SimPO、RLHF/PPO 的适用条件，方向正确。行业对比可进一步明确取舍：

| 方法 | 数据条件 | 主要优势 | 主要风险 | 适用建议 |
| ---- | ---- | ---- | ---- | ---- |
| SFT | 指令-回答对 | 稳定、易实施 | 难以表达偏好 | 基座能力与格式对齐的首选 |
| DPO | 成对偏好数据 | 离线、简单、无需奖励模型 | 易过拟合，依赖偏好对质量 | 有成对偏好且算力有限时优先 |
| ORPO | 指令对 + 偏好 | 单阶段完成 SFT 与对齐 | 数据配比敏感 | 希望减少流程复杂度时使用 |
| KTO | 非配对点赞/点踩 | 数据采集成本低 | 信号噪声较大 | 只有非配对反馈时使用 |
| SimPO | 成对偏好 | 不依赖参考模型，显存友好 | 需校准长度与奖励尺度 | 显存受限场景 |
| RLHF/PPO | 在线奖励模型 | 灵活、可多目标优化 | 不稳定、工程复杂 | 有成熟奖励模型与 KL 监控时使用 |

上述方法均需配套对齐税检查与 checkpoint 级退化评估[cite:18][cite:19]。现有文档提出的「MMLU 5% / GSM8K 8% 作为起点」应被视为**待校准阈值**，不能直接作为所有模型规模的硬标准。

### 3.5 安全与治理：从原则到可检查条款

OWASP GenAI LLM Top 10 2026 于 2026 年 8 月发布，覆盖提示注入、敏感信息泄露、系统提示词泄露等生成式 AI 应用风险，并映射到 NIST、MITRE ATLAS、CWE 等框架[cite:13]。NIST AI 600-1 生成式 AI 风险画像列出 13 类风险与 400 多项行动建议，可作为治理清单[cite:14]。EU AI Act 第 12 条要求高风险 AI 系统具备自动日志能力，以支持全生命周期追溯与事后监管[cite:15]。国内《生成式人工智能服务管理暂行办法》自 2023 年 8 月 15 日施行，对内容安全、训练数据、服务提供者责任提出要求[cite:16]。

**对 YYC3 的启示：**

- 建立「威胁模型 → 控制项 → 日志字段 → 审计报表」的治理链。
- 系统提示词按敏感资产管理：输出侧扫描泄露、输入侧防直接/间接注入、检索与工具输出视为不可信。
- 日志区分元数据与内容，内容日志默认关闭，敏感字段脱敏，保留期限按监管语境设定。
- 高风险场景应支持自动日志、决策台账与确定性重放。

## 四、差距分析

### 4.1 结构性差距

1. **缺少唯一入口。** 两份文档没有 manifest 串联，读者无法判断先读什么、每个文件的验收标准是什么。
2. **域数量与表述不一致。** 原文「六个文件域」与实际八个域不符，本次已修正。
3. **缺少文件级契约。** 每个文件应有输入、输出、依赖、失败模式、验收标准与关联 ID，目前只有章节标题。
4. **缺少交叉引用。** 角色契约、评测口径、日志字段、治理控制项之间没有统一 ID 与追溯链。
5. **缺少版本矩阵。** 提示词、技能、评测集、模型 checkpoint 之间没有不可变引用关系。

### 4.2 内容差距

| 缺口 | 影响 | 建议 |
| ---- | ---- | ---- |
| 内部黄金集缺失 | 无法做业务验收与回归 | 按场景建立正常/边界/对抗/不可达四类用例 |
| 安全威胁模型缺失 | 难以防御注入、泄露、越权、记忆污染 | 建立 OWASP/NIST 映射与红队用例 |
| 工具权限模型缺失 | 工具越权与误操作风险 | 最小权限、写操作人工确认、递归深度上限 |
| 记忆写入规则不足 | 记忆污染与旧结论误用 | 明确哪些记忆可写、何时失效、如何标注来源 |
| 成本与延迟未建模 | 无法做容量与体验规划 | 增加 token、工具调用、P95 延迟、单任务成本指标 |
| 数据治理不足 | 训练/评测数据来源与许可不清 | 记录数据版本、许可、去重、污染标注 |

### 4.3 运行机制差距

- 没有评测运行器与 CI 集成，提示词变更无法自动回归。
- 没有发布门禁，无法判断「是否可以上线」。
- 没有线上抽样与漂移监控，无法发现真实场景退化。
- 没有台账写入与回放，无法重建历史结论。
- 没有变更传播矩阵，修改一个文件后不知道哪些评测必须重跑。

## 五、YYC3 本地自用提示词体系设计

### 5.1 设计原则

1. **规格优先**：系统提示词写目标、判据、边界与回退，不写长篇流程。
2. **唯一入口**：`YYC3-AI-FAmily-Agent-模型架构-总控清单.md` 是唯一入口，记录文件职责、依赖、补全顺序与验收标准。
3. **渐进披露**：技能描述默认只加载摘要，需要执行细节时再加载 `SKILL.md` 主体。
4. **证据分级**：所有结论标注「已验证 / 行业共识 / 推断 / 待验证」。
5. **最小权限**：工具、写操作、跨 Agent 委派均按最小权限授权。
6. **可追溯**：决策、训练、评测、变更均有台账与不可变引用。
7. **可回退**：每个关键动作有失败分类、重试上限、降级与人工升级路径。
8. **可评测**：每个文件、技能、流程都有验收标准与对应评测用例。
9. **安全默认**：检索内容、工具输出、记忆召回均视为潜在不可信输入。
10. **持续校准**：公开基准做体检，内部黄金集做验收，线上抽样做漂移监控。

| 工作记忆 | 当前会话上下文 | 自动 | 受 token 预算约束 |
| 情节记忆 | 历史会话压缩轨迹 | 会话结束或阈值触发 | 按相关性、时效、重要性召回 |
| 语义记忆 | 标准条款、评测知识、内部规范 | 人工评审后写入 | 带出处检索 |
| 程序记忆 | 可复用流程、判据、检查表 | 仅评审闸门通过后写入 | 按任务类型调用 |

摘要采用 L1 单会话、L2 项目级、L3 能力域三层。每层摘要必须附带来源会话 ID、日志 ID 或 checkpoint 引用；推断性内容必须标注「推断」。上下文预算建议设置 70% 触发摘要更新、85% 启用滑动窗口与摘要合并的阈值，但需按模型实测校准。

### 5.6 认知与规划协议

| 机制 | 触发条件 | 输出 | 停止规则 |
| ---- | ---- | ---- | ---- |
| 主动思维 | 任务开始、步骤切换、任务结束 | plan、偏差检查、简短反思 | 计划完成且成功判据满足 |
| 计划-执行 | 多步任务 | 可验证的中间状态 | 连续两次重规划无进展则升级 |
| 自评 | 交付前 | 证据充分性、对齐度、遗漏项、可执行性 | 四级评分，无锚点数值禁止 |
| 反思 | 失败或偏差后 | credit assignment、root cause、next step | 写入情节记忆，不自动改程序记忆 |
| 元认知守卫 | 虚假完成、任务漂移、空洞回答 | 阻止完成、触发重规划、要求补证 | 连续两轮无新事实则声明无法推进 |

### 5.7 技能与工具协议

技能注册表字段建议：`name`、`description`、`input_schema`、`output_schema`、`version`、`dependencies`、`failure_modes`、`owner`。技能文件遵循 `SKILL.md` + YAML frontmatter，主体建议不超过 500 行 / 5000 tokens，成功判据与停止规则必须显式[cite:5][cite:20]。

工具失败处理矩阵：

| 失败类型 | 处理动作 | 重试上限 | 升级条件 |
| ---- | ---- | ---- | ---- |
| 瞬时错误 | 指数退避重试 | 1 次 | 连续失败升级 |
| 参数错误 | 修正参数后再试 | 1 次 | schema 校验失败升级 |
| 权限错误 | 停止并请求授权 | 0 次 | 立即升级 |
| 语义错误 | 缩小任务范围或替换工具 | 1 次 | 仍失败则人工介入 |
| 超时 | 降级或异步重试 | 1 次 | 影响交付则升级 |

写操作、删除操作、跨 Agent 委派必须有人工确认闸门；工具调用链与递归深度设置硬上限。

### 5.8 审计与台账

| 台账 | 关键字段 | 保留建议 |
| ---- | ---- | ---- |
| 日志 | 时间、模型版本、token、延迟、工具名、状态 | 元数据长期保留；内容默认关闭 |
| 决策台账 | decision_id、结论等级、依据、反事实、复核人、有效期 | 3–7 年，按监管语境 |
| 训练落档 | 基座版本、checkpoint hash、数据版本、超参、对齐税 | 3–7 年 |
| 评测运行 | 基准/版本、子集、污染标注、置信边界、delta | 与模型版本同周期 |
| 变更记录 | 变更文件、影响评测、受影响旧结论 | 永久 |

### 5.9 迭代与治理

| 变更类型 | 必须重跑 | 台账影响 |
| ---- | ---- | ---- |
| 角色/契约变更 | 全部黄金集与安全用例 | 标记旧结论需复核 |
| 评测阈值变更 | 相关能力集与回归集 | 旧结论标注「基于旧阈值」 |
| 技能/工具变更 | 工具调用、无关性、失败处理 | 更新技能版本与调用台账 |
| 模型 checkpoint 变更 | 三线退化评估 + 黄金集 | 新建训练落档与评测运行 |
| 安全策略变更 | 红队用例 + 泄露扫描 | 更新合规映射与审计报表 |

### 5.10 运行时接口

```text
用户请求
  → 策略引擎（权限/安全/预算）
  → 模型适配器（系统提示 + 上下文）
  → 技能路由（注册表/渐进披露）
  → 工具适配器（MCP，参数校验/最小权限）
  → 记忆存储（工作/情节/语义/程序）
  → 评测与守卫（成功判据/停止规则/自评）
  → 台账写入（决策/日志/评测）
  → 输出契约（结论/证据等级/下一步）
```

## 六、评测与质量门禁

### 6.1 评测分层

| 层级 | 评测对象 | 示例 | 门禁 |
| ---- | ---- | ---- | ---- |
| L1 单元评测 | 单个提示词/技能 | 格式、约束遵守、停止规则 | 通过才可合并 |
| L2 能力评测 | 模型能力 | MMLU-Pro、GPQA、LiveBench | 基线对比，记录 delta |
| L3 Agent 评测 | 工具与多轮任务 | BFCL V4、τ-bench、SWE-bench | pass^k 与轨迹评估 |
| L4 生产评测 | 真实业务 | 内部黄金集、线上抽样 | 发布门禁与漂移监控 |

### 6.2 指标矩阵

| 维度 | 指标 | 定义 | 目标 |
| ---- | ---- | ---- | ---- |
| 正确性 | Task Success | 任务完成且满足成功判据 | 按场景预注册 |
| 可靠性 | pass^k | 连续 k 次运行均成功的比例 | 高于单次 pass@1 |
| 工具 | Tool-call Accuracy | 工具选择与参数正确率 | 按 BFCL 口径 |
| 工具 | Irrelevance Rate | 无需调用时正确拒绝的比例 | 越低越好 |
| 安全 | Safety Violation | P0/P1 安全违规数 | P0 必须为 0 |
| 可追溯 | Trace Coverage | 有完整决策/证据链的任务比例 | 100% 关键任务 |
| 性能 | P95 Latency | 95 分位响应时间 | 按业务 SLO |
| 成本 | Cost per Task | 单任务 token 与工具成本 | 按预算 |
| 回归 | Regression Delta | 新版本相对基线的变化 | 不超过预注册阈值 |

### 6.3 基准选型

| 基准 | 用途 | 频率 | 注意事项 |
| ---- | ---- | ---- | ---- |
| HELM Capabilities / MMLU-Pro | 基座能力基线 | 每次模型升级 | 静态基准可能饱和[cite:9] |
| LiveBench | 抗污染能力趋势 | 每季度 | 使用最新 release[cite:10][cite:24] |
| BFCL V4 | 工具调用与无关性 | 每次技能/工具变更 | 关注 multi-turn 与 memory[cite:8][cite:23] |
| τ-bench | 工具-用户交互可靠性 | 每次 Agent 流程变更 | 使用 pass^k[cite:11] |
| SWE-bench Verified/Pro | 代码 Agent | 每次代码能力变更 | 注意污染与评分协议[cite:12] |
| 内部黄金集 | 业务验收 | 每次发布 | 覆盖正常/边界/对抗/不可达 |

### 6.4 发布门禁

1. **P0 安全门禁**：出现任一 P0 安全违规，禁止发布。
2. **能力门禁**：公开基准与内部黄金集的 delta 不超过预注册阈值；阈值按模型规模与业务风险校准。
3. **可靠性门禁**：关键任务 pass^k 达到预注册标准，不能只看 pass@1。
4. **可追溯门禁**：关键任务必须有决策台账、证据引用与评测运行记录。
5. **灰度门禁**：新版本先小流量灰度，观察延迟、成本、错误率与安全告警，再全量。

## 八、关键决策与取舍

| 决策 | 选项 | 建议 | 理由 |
| ---- | ---- | ---- | ---- |
| 系统提示词长度 | 单体长提示 vs 规格 + 技能 | 规格 + 技能 | 降低指令衰减与维护成本[cite:3] |
| Agent 形态 | 单 Agent vs 多 Agent | 先单 Agent，按需 A2A | 降低协作复杂度，先保证可靠性 |
| 评测依据 | 公开基准 vs 内部黄金集 | 两者并用 | 公开基准做体检，黄金集做验收[cite:17] |
| 对齐方法 | 离线偏好 vs 在线 RLHF | 按数据条件选择 | DPO/KTO/ORPO/SimPO 成本更低，PPO 需稳定性保障[cite:18] |
| 治理强度 | 轻量 vs 强制门禁 | 风险分级 | P0 硬门禁，P1 警告与复核 |
| 记忆写入 | 自动 vs 评审后写入 | 程序记忆必须评审 | 防止错误流程固化[cite:5] |

## 九、风险与反模式

- **提示词膨胀**：把所有流程塞进系统提示词，导致指令衰减与维护困难。
- **基准过拟合**：只优化公开基准分数，忽视真实业务与污染风险。
- **工具过度调用**：为表现主动而调用无关工具，需用 BFCL 的无关性检测思路约束[cite:8]。
- **记忆污染**：把未验证结论写入长期记忆，后续会话反复放大。
- **日志泄露**：把系统提示词、密钥、PII 写入日志，违反 OWASP 与合规要求[cite:13]。
- **虚假完成**：工具返回成功但语义结果不满足成功判据，仍标记完成。
- **未版本化**：提示词、技能、评测集、模型 checkpoint 没有不可变引用，无法复现。
- **单指标优化**：只看准确率，不看可靠性、安全、延迟与成本。

## 十、结论与建议

### 10.1 结论

YYC3 现有两份文档已经具备「角色契约 + 文件域大纲」的体系雏形，方向与行业最佳实践一致；主要差距不在理念，而在**可执行性**：缺少 manifest、文件级契约、评测资产、运行接口、日志台账与发布门禁。建议以「1 + 8 + 3」架构完成工程化闭环。
